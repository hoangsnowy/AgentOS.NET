# AgentOS.NET REST API

The Api host (`src/AgentOs.Api`) serves a versioned REST API, an MCP endpoint at `/mcp`, and the paired-runner
SignalR hub. This page is the contract: how versions work, how to authenticate (people and machines), and what
happens when something is deprecated.

- **Current version:** `v1` — every route is under `/v1/…`.
- **OpenAPI:** [`docs/api/openapi-v1.json`](api/openapi-v1.json) (committed, reviewed with each change) and live at
  `/openapi/v1.json` + the Scalar UI at `/scalar/v1` outside Production.

## Versions

| Path | Status | Notes |
|---|---|---|
| `/v1/<route>` | **current** | The contract. Named operations, documented in `openapi-v1.json`. |
| `/<route>` (no version) | **deprecated** since 2026-11-03, sunset **2027-05-03** | The same handlers. Still work; answer with deprecation headers (below). Not in the OpenAPI document. |
| `/`, `/version`, `/health`, `/alive`, `/health/llm` | unversioned | Operational probes — never versioned, never deprecated. |
| `/mcp` | unversioned | MCP (Streamable HTTP) — versioned by the MCP protocol itself. |
| `/hubs/remote-agent` | unversioned | Paired-runner SignalR hub — versioned by its own wire contract. |

Every module's REST routes are mapped through `ModuleLoader.MapVersionedModuleEndpoints`
(`src/AgentOs.SharedKernel/Modularity/ModuleLoader.cs`): once under `/v1` and once at the old path with
`ApiDeprecationMetadata`. A module whose endpoints are a protocol (a SignalR hub) implements
`IProtocolEndpointModule` and is mapped once, at its own path.

### Deprecation headers

A response from a deprecated route carries:

```http
Deprecation: @1793664000
Sunset: Mon, 03 May 2027 00:00:00 GMT
Link: </v1/tenants/me>; rel="successor-version", <https://github.com/hoangsnowy/AgentOS.NET/blob/main/docs/API.md#deprecation-policy>; rel="deprecation"; type="text/html"
```

- `Deprecation` ([RFC 9745](https://www.rfc-editor.org/rfc/rfc9745)) — when the route was deprecated (an RFC 9651
  date: `@` + Unix seconds).
- `Sunset` ([RFC 8594](https://www.rfc-editor.org/rfc/rfc8594)) — the earliest date it may stop working.
- `Link rel="successor-version"` — the route to call instead; `rel="deprecation"` — this policy.

The headers are added before authentication, so a `401`, `403` or `429` from a deprecated route says so too.
Clients should log or alert on any response that carries `Deprecation`.

## Deprecation policy

1. **Within a version, changes are additive only.** New routes, new optional request fields and new response fields
   may appear in `v1` at any time; clients must ignore unknown response fields. Removing or renaming a route, a
   required field or a response field, or changing a field's type or meaning, is a breaking change.
2. **A breaking change ships as a new version** (`/v2/…`) next to the old one. The old version's routes are then
   marked deprecated and keep working.
3. **Minimum notice: six months** from the first release that announces the deprecation to the `Sunset` date, and
   never removed in a patch release. The `Deprecation` and `Sunset` headers, this page and the
   [CHANGELOG](../CHANGELOG.md) (**Deprecated** section, with a migration note) announce it together.
4. **After the sunset date** the route may be removed in the next minor or major release; removals are listed under
   **Removed** in the CHANGELOG with the successor route.
5. **Security exception.** A route that cannot be made safe may be withdrawn sooner; the CHANGELOG **Security**
   section says why and what to use instead.
6. **The committed OpenAPI document is the review gate.** `docs/api/openapi-v1.json` is regenerated by a test
   (`ApiV1IntegrationTests`, `AGENTOS_UPDATE_OPENAPI=1`) and the test fails when the running Api no longer matches
   it — so every contract change shows up as a diff in the pull request and is reviewed against rule 1.

The unversioned routes that existed before `v1` are the first deprecation under this policy: deprecated
2026-11-03, sunset 2027-05-03.

## Authentication

Every route except the operational probes and the public sign-up / invitation-preview routes needs
`Authorization: Bearer <token>`. The Api accepts two kinds of bearer token on the same header:

| Token | Who | How it is checked |
|---|---|---|
| Keycloak access token (JWT, RS256) | people (the desktop, Scalar) | signature against the realm JWKS, issuer, audience, lifetime |
| AgentOS.NET API token `aos_<prefix>_<secret>` | scripts, CI, the VS Code extension, MCP clients | prefix lookup → salted-HMAC compare in constant time → not revoked, not expired |

`Bearer aos_…` is forwarded from the JWT scheme to the API-token scheme
(`ApiTokenAuthentication.AddApiTokenAuthentication`), so nothing else changes for callers: the principal carries the
same `tenant`, `sub`, name and role claims a JWT would.

### API tokens

Created in the desktop, **Settings → People & data → API tokens**:

- **Personal token** — any member. Acts as that member (`sub` = their user id; runs are attributed to them). Revoked
  automatically when the member is removed from the workspace.
- **Service account** — workspace admins only. A workspace identity for CI (`sub` = `apitoken:<id>`, name
  `service:<name>`), not tied to a person.

Each token has a **scope** (closed upwards — admin includes run includes read):

| Scope | Allows |
|---|---|
| `read` | `GET` / `HEAD` / `OPTIONS` — runs, results, settings views, `/v1/tenants/me` |
| `run` | also `POST` / `PUT` / `PATCH` / `DELETE` — start pipeline runs, upload ticket files, call `/mcp` |
| `admin` | also the workspace-admin routes (the principal gets the `admin` role). Admins only. Never `platform-admin`. |

A request whose method needs a scope the token lacks gets `403` (`application/problem+json`, *Insufficient token
scope*). An invalid, revoked or expired token gets `401` with `WWW-Authenticate: Bearer error="invalid_token"`.

The plaintext is shown **once** at creation; only a salted HMAC-SHA256 is stored. Every token expires — at most
`Tenants:ApiTokens:MaxLifetimeDays` (platform setting, default 366 days; see [CONFIG.md](CONFIG.md)). Creation,
revocation and use are audited (**Settings → Audit log**: `apitoken.created`, `apitoken.revoked`, `apitoken.used`,
`apitoken.refused`; use and refusal rows are written at most once per token per 5 minutes, with the caller's IP and
user agent). The token list shows when each token was last used.

Check what a token resolves to:

```bash
curl -s -H "Authorization: Bearer $AGENTOS_TOKEN" https://agentos.example.com/v1/tenants/me
# {"tenantId":"acme","userId":"apitoken:…","userName":"service:ci-deploy","roles":["member"],
#  "isAuthenticated":true,"isAdmin":false,"authMethod":"api_token","scopes":["read","run"]}
```

### CI: start a run with a service account

Create a service account with the `run` scope, store it as a CI secret, and call the Api:

```yaml
# .github/workflows/agentos.yml
jobs:
  agentos:
    runs-on: ubuntu-latest
    steps:
      - name: Run the AgentOS.NET pipeline
        env:
          AGENTOS_URL: https://agentos.example.com
          AGENTOS_TOKEN: ${{ secrets.AGENTOS_TOKEN }}
        run: |
          curl --fail-with-body -sS -X POST "$AGENTOS_URL/v1/pipeline" \
            -H "Authorization: Bearer $AGENTOS_TOKEN" -H "Content-Type: application/json" \
            -d '{"description":"As a user I can reset my password by email"}'
```

`/v1/pipeline/stream` returns the same run as Server-Sent Events (`progress`, `result`, `error`).

### VS Code extension

The **AgentOS.NET Runner** extension (`tools/agentos-vscode`) uses a personal token for API calls:
**AgentOS.NET: Set API token** stores it in VS Code secret storage (checked against `/v1/tenants/me`),
**Run the pipeline on a user story** calls `POST /v1/pipeline`, **Check API token** / **Clear API token** manage it.
Set `agentos.apiUrl` to the Api's base URL.

## Errors

Errors are RFC 7807 `application/problem+json` (`status`, `title`, `detail`, `traceId`); validation failures are
`400` with an `errors` map. `402` means the workspace's monthly budget cap is reached; `429` is the per-tenant rate
limit (120 requests/minute on the Api).
